# نموذج البيانات (مسودة للمراجعة)

> **الحالة:** تصميم مبدئي — **الجداول النهائية تُؤجَّل** حتى نستوفي العلاقات والفهارس وسياسات RLS ونراجعها باختبارات فعلية.
> **قاعدة:** فصل منطقي للوحدات، ومصدر ورخصة لكل محتوى، وسلطة الخادم في العدّ والصلاحيات.

---

## 1. قرارات قاعدة البيانات المعتمدة

| # | القرار |
| --- | --- |
| DB-1 | لا تُخزَّن كلمات مرور Google أو بيانات دخول قنوات YouTube إطلاقًا |
| DB-2 | رموز OAuth في **مخزن أسرار** خادمي مشفّر، لا تُعرض للعميل ولا تدخل السجلات |
| DB-3 | **لا عدّاد في المتصفح** لتحديد العمليات المجانية — الخادم يسجّل الاستهلاك ويمنع التكرار |
| DB-4 | كل مادة لها صف في `content_sources` بالرخصة وحقوق المعالجة (انظر `04-content-sources.md`) |
| DB-5 | حدود احتفاظ واضحة للملفات وبيانات التحليلات + آلية حذف بيانات المستخدم |
| DB-6 | كل عملية حساسة تُسجَّل في `audit_logs` (من، ماذا، متى، من أي جلسة) |
| DB-7 | تأخير الجداول النهائية حتى مراجعة العلاقات والفهارس وRLS |

## 2. الوحدات والجداول

### 2.1 الحسابات والأمان
| الجدول | الغرض | ملاحظات |
| --- | --- | --- |
| `profiles` | الملف العام لحساب المستخدم | مرتبط بجنسية الحساب (موثق/بريد) |
| `user_preferences` | اللغة، المظهر، الإشعارات، الخصوصية | لغة الواجهة = `ar`/`en` |
| `user_roles` | الأدوار (`user`, `reviewer`, `moderator`, `admin`) | منهجية RBAC فوق RLS |
| `sessions` | جلسات النشطة والأجهزة | إمكانية إنهاء جلسة محددة |
| `audit_logs` | سجل التدقيق | لا يُعدَّل ولا يُحذف (append-only) |

### 2.2 المحتوى (القرآن والمكتبة)
| الجدول | الغرض | ملاحظات |
| --- | --- | --- |
| `content_sources` | المصدر + الرخصة + حقوق المعالجة + حالة التحقق | **أساسي، ويُملأ قبل أي استيراد** |
| `content_items` | قطعة المحتوى (سورة، حديث، تفسير، درس…) | نوع + حالة مراجعة |
| `content_versions` | إصدارات المحتوى (نص/ترجمة/صوت) | يربط المصدر والإصدار |
| `content_reviews` | قرارات المراجعة (مراجع، قرار، وقت، ملاحظة) | مرتبط بـ `audit_logs` |

### 2.3 القرآن والعبادات (بيانات شخصية اختيارية)
| الجدول | الغرض |
| --- | --- |
| `bookmarks` | علامات القراءة (آية/صفحة) |
| `reading_progress` | موضع القراءة وتقدم السور |
| `daily_goals` | أهداف يومية (صفحات/سورة) |

### 2.4 التعليم
`courses`, `lessons`, `enrollments`, `quiz_attempts` — الملكية والتقدم يُحفظان للطالب والمالك فقط.

### 2.5 الصوتيات (مسار B — تُؤجَّل التعبئة)
`audio_jobs`, `audio_assets`, `audio_outputs`, `audio_usage`
> **فصل الأصل عن الناتج:** الأصل = ملف المستخدم/المصدر المرخّص، الناتج = ما أنتجته المعالجة. لكل منهما سجل احتفاظ وحذف منفصل.

### 2.6 Creator Studio (مسار B — تُؤجَّل التعبئة)
`creator_channels`, `creator_projects`, `video_assets`, `publishing_jobs`
> لا تخزين لبيانات اعتماد القناة (DB-1)؛ يُخزَّن معرّف القناة وحالة التفويض فقط.

### 2.7 الوكيل (مسار B)
`agent_tasks`, `agent_runs`, `agent_approvals`
> كل تشغيل يسجّل الأدوات المُستخدَمة ونتيجته؛ الموافقة شرط للعمليات الحساسة.

### 2.8 الاشتراكات والتشغيل
`plans`, `subscriptions`, `usage_ledger` · `notifications`, `support_tickets`
> `usage_ledger` هو مصدر الحقيقة للحصص (DB-3) — قراءة من الخادم فقط.

## 3. مخطط العلاقات (ملخّص)

```
profiles ─┬─ user_preferences
          ├─ user_roles
          ├─ sessions
          ├─ bookmarks / reading_progress / daily_goals
          ├─ enrollments ── courses ── lessons ── quiz_attempts
          ├─ subscriptions ── plans
          ├─ usage_ledger
          └─ agent_tasks ── agent_runs ── agent_approvals

content_items ─┬─ content_versions ── content_sources
               ├─ content_reviews ── audit_logs
               └─ (bookmarks → content_items)

audio_jobs ─┬─ audio_assets   (الأصل + رخصته)
            └─ audio_outputs  ── audio_usage

creator_channels ── creator_projects ─┬─ video_assets
                                      └─ publishing_jobs
```

## 4. سياسات RLS (النمط المعتمد)

**النمط:** كل استعلام من التطبيق يمرّ بثلاث خطوات إلزامية داخل معاملة واحدة (`src/lib/db.ts`):

```sql
BEGIN;
SET LOCAL ROLE app_client;                          -- 1) دور غير مالك (المالك يتجاوز RLS)
SELECT set_config('app.user_id', '<uuid>', true);   -- 2) سياق المستخدم
SELECT set_config('app.user_role', 'user', true);   -- 3) سياق الدور التطبيق
-- ... الاستعلامات ...
COMMIT;
```

```sql
-- مثال: العلامات لا تُرى إلا لصاحبها
CREATE POLICY bookmarks_owner_all ON bookmarks
  FOR ALL TO authenticated_app
  USING (user_id = current_setting('app.user_id', true)::uuid)
  WITH CHECK (user_id = current_setting('app.user_id', true)::uuid);
```

| مستوى | القاعدة |
| --- | --- |
| قراءة عامة | محتوى المحتوى المنشور (`content_items` بحالة `published`) — بلا RLS خاص |
| بيانات شخصية | ملكية صارمة: `user_id = current_setting('app.user_id')` |
| أدوار إدارية | فحص الدور من `user_roles` داخل السياسة، لا من طلب المتصفح |
| محتوى قيد المراجعة | لا يُقرأ إلا للأدوار المصرّح بها |
| جداول التكامل (مسار B) | قراءة للملك، وكتابة لسير العمل الداخلي فقط |

**شرط القبول لـ RLS:** اختبارات تثبت أن:
1. مستخدم أ لا يقرأ بيانات مستخدم ب.
2. تغيير `app.user_id` عبر طلب المتصفح لا يُقبل (الخادم هو من يضبطه).
3. مستخدم عادي لا يصل لجدول أدواره أو سجل التدقيق.
4. كل سياسة مفعّلة في بيئة الاختبار (لا RLS معطَّل صامتًا).

## 5. الفهارس المقترحة (تُراجع مع الاستعلامات الفعلية)

- `content_items (type, status)` + فهرس نصي للبحث (`pg_trgm` أو FTS عربي).
- `content_versions (content_item_id, edition)`.
- `bookmarks (user_id, content_item_id)` فريد.
- `reading_progress (user_id, content_item_id)`.
- `audit_logs (created_at)` + `(user_id, created_at)`.
- `usage_ledger (user_id, period)` — أساس احتساب الحصص.
- الفهارس النصية العربية تُقاس أثرها على البحث قبل الاعتماد.

## 6. الاحتفاظ والحذف

| البيانات | الاحتفاظ | الحذف |
| --- | --- | --- |
| ملفات المعالجة المؤقتة (مسار B) | حتى انتهاء المعالجة + مهلة قصيرة | حذف تلقائي مُختبَر (POC) |
| بيانات التحليلات (مسار B) | مدة محددة تُعلن في سياسة الخصوصية | حذف دوري |
| حساب المستخدم | حتى طلب الحذف | حذف: بيانات شخصية + إبقاء السجلات التشغيلية المجهّلة حسب السياسة |
| `audit_logs` | حسب المتطلبات التنظيمية | غير قابل للحذف من الواجهة (append-only) |

## 7. بيئة التشغيل

**المسار المعتمد:** Supabase (Postgres مُدار) — راجع `docs/08-supabase-setup.md` للخطوات ونقاط الاستبدال.

| البيئة | الغرض |
| --- | --- |
| `development` | عمل يومي على قاعدة التطوير في Supabase، بيانات تجريبية |
| `test` | اختبارات آلية معزولة — تُشغَّل على Postgres مدمج (PGlite) أو على قاعدة حقيقية عبر `TEST_DATABASE_URL` |
| `production` | الإنتاج فقط — لا بيانات تجريبية |

**بديل محلي:** `docker-compose.yml` يظل متاحًا للتطوير بدون إنترنت أو بدون حساب Supabase، ونفس الترحيلات تعمل عليه دون أي تعديل.

**متطلب تشغيلي:** بيانات الاتصال (`DATABASE_URL`) في `.env` غير المرحّل فقط، مع `?sslmode=require` عند استخدام Supabase.

---

## 8. ما يُؤجَّل عمدًا

- جداول الصوتيات وCreator Studio والوكيل والاشتراكات: **الهيكل فقط** في التصميم، والتعبئة بعد POC.
- قرارات الفهارس النهائية بعد قياس الاستعلامات.
- تفعيل RLS لكل جدول بعد كتابة اختباراته (لا جدول بلا اختبار).
