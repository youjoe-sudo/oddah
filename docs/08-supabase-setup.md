# إعداد Supabase وطريقة الاستبدال لاحقًا

> **القرار (2026-10-26):** نعتمد **Supabase كقاعدة بيانات مُدارة فقط** (Postgres + RLS)، مع الإبقاء على طبقة الوصول الحالية في `src/lib/db.ts` لسهولة الاستبدال لاحقًا.
> **خارج النطاق حاليًا:** Supabase Auth وStorage وRealtime — تُراجَع عند بناء `CORE-01` والملفات الصوتية.

---

## 1. لماذا هذا التصميم

| الطبقة | الموجود | عند الاستبدال |
| --- | --- | --- |
| الوصول للقاعدة | `withSession()` في `src/lib/db.ts` | **لا يتغير** — تُبدَّل قيمة `DATABASE_URL` فقط |
| العزل والأمان | سياسات RLS قياسية في SQL (`db/migrations/*.sql`) | تنتقل كما هي لأي Postgres آخر |
| المصادقة والملفات | لم تُبنَ بعد | قرار مستقل يُؤجَّل (لا ربط مبكر بمزود) |

**القاعدة:** كل SQL المكتوب قياسي (بدون امتدادات خاصة بـ Supabase)، فتبقى خيارية التغيير حقيقية لا شعارًا.

---

## 2. خطوات الربط (عند إنشاء المشروع)

1. أنشئ مشروع Supabase واختر **أقرب منطقة** لمستخدمي الخدمة.
2. لوحة التحكم → **Connect** → انسخ **Session pooler** (المنفذ `5432`) أو الاتصال المباشر.
3. أضف `?sslmode=require` في آخر الرابط.
4. ضع الرابط في `.env` → `DATABASE_URL`.
5. شغّل الترحيلات: `npm run db:migrate`
6. تحقّق من RLS على القاعدة الحقيقية:
   ```bash
   TEST_DATABASE_URL="<نفس الرابط>" npm test
   ```
   تُشغِّل نفس الاختبارات الثمانية ضد القاعدة الحقيقية ثم تُنظّف بياناتها.

### نصيحة اختيار نوع الاتصال
| النوع | متى |
| --- | --- |
| **Session pooler (5432)** | **الموصى به** — جلساتنا تعتمد `BEGIN/COMMIT` + `SET LOCAL ROLE` |
| Transaction pooler (6543) | أخفّ حملًا، لكنه مصمم لاستعلامات معزولة؛ تجنبه مع جلساتنا الطويلة نسبيًا |
| Direct (5432 + IPv4) | أدق للتطوير، لكنه مقيّد بقائمة IPv4 في بعض الخطط |

## 3. ما يفعله الترحيل على Supabase

| الإجرية | الغرض |
| --- | --- |
| `CREATE EXTENSION citext` | بريد حساس لحالة الأحرف |
| `CREATE ROLE app_client NOLOGIN` | دور غير مالك — **بدونه تتجاوز RLS كل شيء** |
| `GRANT app_client TO <دور الاتصال>` | يسمح بـ `SET LOCAL ROLE app_client` |
| `GRANT ... ON ALL TABLES` | صلاحيات الدور في حدود مطلوبة |
| `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + السياسات | العزل على مستوى القاعدة |

> على Supabase دور الاتصال هو `postgres` (ليس superuser)، والأدوار المخصّزة ميزة موثّقة. إن رُفض `CREATE ROLE`، أنشئ الدور من لوحة الأدوار ثم أعد الترحيل.

## 4. أخطاء شائعة وحلولها

| الخطأ | السبب | الحل |
| --- | --- | --- |
| `password authentication failed` / `SSL required` | رابط بلا `sslmode` | أضف `?sslmode=require` |
| `permission denied to set parameter "app.user_id"` | الدور لا يملك إعداد السياق | تأكد أن الترحيل نجح وأن `DB_CLIENT_ROLE` صحيح |
| `role "app_client" does not exist` | الترحيل لم يُطبَّق | `npm run db:migrate` |
| `permission denied to role app_client` | لا عضوية في الدور | شغّل الترحيل (يمنح العضوية تلقائيًا) |
| `remaining connection slots reserved` | اتصالات فوق الحد | خفّض `max` في `Pool` أو استخدم الـ pooler |
| العزل "لا يعمل" رغم أن الاختبارات خضراء | متصل بدور مالك مع `SET ROLE` مفقودة | لا تعدّل `withSession` — فحص `SET LOCAL ROLE` إلزامي |

## 5. الأمان أثناء العمل على Supabase

- [ ] `DATABASE_URL` في `.env` فقط (الملف مُستثنى من git).
- [ ] لا مفتاح `service_role` في هذا المسار إطلاقًا (نستخدم Postgres مباشرًا).
- [ ] مفتاح `anon` إن ظهر لاحقًا يُعامل كعام مكشوف.
- [ ] تفعيل Point-in-Time Recovery / النسخ الاحتياطي من إعدادات المشروع قبل الإنتاج.
- [ ] اختبار استعادة نسخة احتياطية موثّق (معيار قبول المرحلة صفر).
- [ ] مراجعة ربع سنوية: `SELECT * FROM pg_policies` والتأكد أن كل جدول مفعّل له `rowsecurity = true`.

---

## 6. مسار الاستبدال (عند الحاجة)

1. أنشئ أي Postgres آخر (مضيف خاص، AWS RDS، غيره).
2. شغّل `db/migrations` عليه — الترحيلات قياسية.
3. غيّر `DATABASE_URL` في البيئة المعنية.
4. شغّل `TEST_DATABASE_URL=... npm test` للتأكد من بقاء العزل.
5. **لا تغيير في كود التطبيق** إلا لو اختلف اسم الدور (`DB_CLIENT_ROLE`).

> نقطة الارتباط الوحيدة المتعمّدة: `src/lib/db.ts` + متغيّرات البيئة. أي شيء آخر مكتوب ليبدو قابلًا للنقل.
